# PromptShield — Database Schema Design

## 1. Purpose

This document defines the proposed relational database schema for PromptShield using Azure SQL Database.

The schema supports user authentication, registered applications and endpoints, detection rules, security policies, inspected-request events, threat findings, audit records, and dashboard analytics.

The initial MVP supports a single organization. Multi-tenant support is outside the current scope.

**Status:** Proposed design pending faculty approval and implementation verification.

## 2. Database Conventions

- Database: Azure SQL Database.
- Primary keys: `BIGINT IDENTITY(1,1)` unless otherwise specified.
- Timestamps: `DATETIME2(3)` stored in UTC.
- Boolean values: `BIT`.
- Risk scores: integers between 0 and 100.
- Rule weights: non-negative integers.
- Text: `NVARCHAR` for Unicode support.
- Foreign keys shall preserve referential integrity.
- User passwords shall be stored as password hashes, never plaintext.
- Secrets, passwords, access tokens, and signing keys shall not be stored in security-event evidence.
- Database access shall use parameterized queries.
- Schema changes shall be applied through version-controlled migrations.

## 3. Entity Overview

The database contains the following tables:

1. `Users`
2. `Applications`
3. `Endpoints`
4. `DetectionRules`
5. `SecurityPolicies`
6. `SecurityEvents`
7. `ThreatFindings`
8. `AuditLogs`

The `Organizations` table is intentionally omitted because the MVP supports one organization.

## 4. Table Definitions

### 4.1 Users

Stores users who can sign in to the PromptShield dashboard.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `user_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `email` | `NVARCHAR(254)` | Required; unique after normalization |
| `password_hash` | `NVARCHAR(255)` | Required; generated by a suitable password-hashing library |
| `role` | `VARCHAR(20)` | Required; `Admin`, `Analyst`, or `Viewer` |
| `is_active` | `BIT` | Required; default `1` |
| `created_at` | `DATETIME2(3)` | Required; UTC creation time |
| `updated_at` | `DATETIME2(3)` | Required; UTC update time |

Rules:

- Normalize email addresses consistently before storing them.
- Enforce uniqueness using a database unique constraint or unique index on the normalized email value.
- Use a modern password-hashing algorithm such as Argon2id through a maintained library.
- Do not return password hashes from API responses.
- Inactive accounts must not authenticate or access protected resources.
- Role authorization must be enforced by the backend.

### 4.2 Applications

Stores the applications registered for inspection by PromptShield.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `application_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `name` | `NVARCHAR(150)` | Required |
| `description` | `NVARCHAR(500)` | Optional |
| `is_active` | `BIT` | Required; default `1` |
| `created_by` | `BIGINT` | Foreign key to `Users.user_id` |
| `created_at` | `DATETIME2(3)` | Required; UTC |
| `updated_at` | `DATETIME2(3)` | Required; UTC |

Rules:

- Application names must be validated.
- Only active registered applications can receive inspected requests.
- Deactivation must prevent new inspection or forwarding for that application.
- Deactivation must not delete historical security events.

### 4.3 Endpoints

Stores approved endpoint definitions associated with registered applications.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `endpoint_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `application_id` | `BIGINT` | Required; foreign key to `Applications.application_id` |
| `path_pattern` | `NVARCHAR(500)` | Required; approved path or route pattern |
| `http_method` | `VARCHAR(10)` | Required; normalized HTTP method |
| `description` | `NVARCHAR(500)` | Optional |
| `is_active` | `BIT` | Required; default `1` |
| `created_at` | `DATETIME2(3)` | Required; UTC |

Rules:

- Each endpoint belongs to exactly one application.
- Endpoint paths and HTTP methods must be validated.
- Use a unique constraint on `(application_id, path_pattern, http_method)` unless the application explicitly permits duplicate definitions.
- The MVP shall not use arbitrary user-provided URLs as forwarding destinations.
- Endpoint registration alone does not authorize network access to an arbitrary host.

### 4.4 DetectionRules

Stores the rule definitions used by the detection engine.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `rule_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `name` | `NVARCHAR(120)` | Required; unique |
| `category` | `VARCHAR(40)` | Required; detection category |
| `description` | `NVARCHAR(500)` | Optional |
| `severity` | `VARCHAR(20)` | Required; `Low`, `Medium`, `High`, or `Critical` |
| `weight` | `INT` | Required; non-negative |
| `is_critical` | `BIT` | Required; default `0` |
| `is_enabled` | `BIT` | Required; default `1` |
| `created_at` | `DATETIME2(3)` | Required; UTC |
| `updated_at` | `DATETIME2(3)` | Required; UTC |

Initial categories:

- `SQL_INJECTION`
- `XSS`
- `PATH_TRAVERSAL`
- `COMMAND_INJECTION`
- `PROMPT_INJECTION`
- `SENSITIVE_DATA`
- `RATE_LIMIT`

Rules:

- Rule names must be unique.
- Weights must be non-negative integers.
- A finding associated with a critical rule triggers the critical-rule blocking override.
- Only enabled rules participate in new inspections.
- Changes to a rule must not silently rewrite the meaning of historical findings. Store the relevant rule name, category, severity, and weight snapshot in each finding.

### 4.5 SecurityPolicies

Stores the inspection policy configuration.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `policy_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `name` | `NVARCHAR(120)` | Required; unique |
| `description` | `NVARCHAR(500)` | Optional |
| `risk_threshold` | `INT` | Required; range 0–100; default 50 |
| `is_enabled` | `BIT` | Required; default `1` |
| `created_by` | `BIGINT` | Foreign key to `Users.user_id` |
| `created_at` | `DATETIME2(3)` | Required; UTC |
| `updated_at` | `DATETIME2(3)` | Required; UTC |

Rules:

- The MVP shall have a documented default policy.
- Every inspected event should reference the policy used for its decision.
- `risk_threshold` must be constrained to the range 0–100.
- A critical finding always causes a Block decision, regardless of the configured threshold.
- If multiple policies are introduced later, policy selection and precedence must be deterministic.
- Policy changes must be restricted to authorized administrators and recorded in audit logs.
- The policy used for an event must be identifiable even if its configuration changes later.

### 4.6 SecurityEvents

Stores the inspection result for each processed request.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `event_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `application_id` | `BIGINT` | Required; foreign key to `Applications.application_id` |
| `endpoint_id` | `BIGINT` | Optional; foreign key to `Endpoints.endpoint_id` |
| `policy_id` | `BIGINT` | Required; foreign key to `SecurityPolicies.policy_id` |
| `request_time` | `DATETIME2(3)` | Required; time the request was observed, UTC |
| `created_at` | `DATETIME2(3)` | Required; event-record creation time, UTC |
| `risk_score` | `INT` | Required; range 0–100 |
| `decision` | `VARCHAR(10)` | Required; `Allow` or `Block` |
| `reason_code` | `VARCHAR(50)` | Required; machine-readable decision reason |
| `correlation_id` | `UNIQUEIDENTIFIER` | Required; identifier used to trace a request |
| `http_method` | `VARCHAR(10)` | Optional; normalized HTTP method |
| `request_path` | `NVARCHAR(500)` | Optional; sanitized path, excluding query secrets |
| `processing_status` | `VARCHAR(20)` | Required; `Completed` or `Failed` |

Rules:

- The risk score must be between 0 and 100.
- Decisions must be `Allow` or `Block`.
- `request_time` and `created_at` have different meanings and must not be treated as interchangeable.
- A null `endpoint_id` is permitted only when the request cannot be mapped to a registered endpoint and is rejected or recorded according to the documented inspection flow.
- `policy_id` is required so that the decision can be traced to a policy.
- Store only the minimum request information needed for security analysis.
- Do not persist raw authorization headers, passwords, tokens, or unnecessary sensitive request bodies.
- The event and its threat findings must be persisted in one database transaction.
- A request must not be forwarded if required event persistence fails.
- A failed processing attempt may be logged separately through safe operational logging; it must not be falsely reported as a successfully persisted security event.
- `correlation_id` should be indexed for support and investigation.

### 4.7 ThreatFindings

Stores individual detection findings associated with an inspection event.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `finding_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `event_id` | `BIGINT` | Required; foreign key to `SecurityEvents.event_id` |
| `rule_id` | `BIGINT` | Optional; foreign key to `DetectionRules.rule_id` |
| `rule_name_snapshot` | `NVARCHAR(120)` | Required; rule name at inspection time |
| `category_snapshot` | `VARCHAR(40)` | Required; category at inspection time |
| `severity_snapshot` | `VARCHAR(20)` | Required; severity at inspection time |
| `weight_snapshot` | `INT` | Required; non-negative weight at inspection time |
| `is_critical_snapshot` | `BIT` | Required; critical status at inspection time |
| `confidence` | `DECIMAL(4,3)` | Optional; range 0.000–1.000 |
| `evidence_summary` | `NVARCHAR(1000)` | Optional; sanitized summary |
| `created_at` | `DATETIME2(3)` | Required; UTC |

Rules:

- Each finding belongs to one security event.
- A finding may reference a current detection rule, but its snapshot fields preserve historical meaning.
- A finding's weight and critical status must reflect the rule configuration used for that inspection.
- Confidence may be null when a detector does not provide a meaningful confidence estimate.
- When present, confidence must be between 0 and 1.
- Evidence summaries must be sanitized and must not expose secrets or unnecessary sensitive data.
- Deleting an event for retention purposes may delete its associated findings in the same transaction.
- Deleting or disabling a detection rule must not erase historical findings.

### 4.8 AuditLogs

Records important administrative and security-relevant actions.

| Column | SQL type | Constraints / purpose |
|---|---|---|
| `audit_id` | `BIGINT IDENTITY(1,1)` | Primary key |
| `user_id` | `BIGINT` | Optional; foreign key to `Users.user_id` |
| `action` | `VARCHAR(80)` | Required; action identifier |
| `entity_type` | `VARCHAR(50)` | Optional; affected entity type |
| `entity_id` | `NVARCHAR(100)` | Optional; affected entity identifier |
| `outcome` | `VARCHAR(20)` | Required; `Success` or `Failure` |
| `correlation_id` | `UNIQUEIDENTIFIER` | Optional; request correlation |
| `created_at` | `DATETIME2(3)` | Required; UTC |
| `details_summary` | `NVARCHAR(1000)` | Optional; sanitized summary |

Rules:

- Record actions such as login outcomes, user-role changes, policy changes, application changes, and detection-rule changes.
- Do not store passwords, tokens, signing secrets, or raw sensitive request bodies in audit details.
- Application roles must not be able to modify or delete audit records arbitrarily.
- Retention for audit logs shall be defined separately from the 30-day security-event retention proposal.
- If a user account is removed, historical audit records should remain available. Prefer deactivating accounts and using an appropriate foreign-key deletion policy.

## 5. Relationships

- `Users` 1 → many `Applications` through `created_by`.
- `Users` 1 → many `SecurityPolicies` through `created_by`.
- `Users` 1 → many `AuditLogs` through `user_id`.
- `Applications` 1 → many `Endpoints`.
- `Applications` 1 → many `SecurityEvents`.
- `Endpoints` 1 → many `SecurityEvents`, where an event may have no mapped endpoint.
- `SecurityPolicies` 1 → many `SecurityEvents`.
- `SecurityEvents` 1 → many `ThreatFindings`.
- `DetectionRules` 1 → many `ThreatFindings`, where a historical finding may retain a null `rule_id` only if the referenced rule has been retired under a documented preservation strategy.

### Application and Endpoint Consistency

An event's `endpoint_id`, when present, must refer to an endpoint belonging to the same `application_id` recorded on the event.

Enforce this through a composite foreign key, using a unique candidate key on `(application_id, endpoint_id)` in `Endpoints`, or validate the relationship within a controlled database transaction. The implementation must not rely on unchecked frontend validation.

## 6. Risk Scoring and Decision Rules

For an inspection, calculate:

`risk_score = MIN(100, SUM(applicable finding weights))`

If no findings apply, the risk score is 0.

Decision logic:

1. If any applicable finding has `is_critical_snapshot = 1`, return `Block`.
2. Otherwise, if `risk_score >= policy.risk_threshold`, return `Block`.
3. Otherwise, return `Allow`, subject to any explicitly configured mandatory-block policy.
4. If a required inspection, policy, or persistence step fails, do not forward the request.

The policy engine must be the single authoritative source of the final decision. The frontend must not independently calculate or override it.

The database must store the final score, decision, reason code, policy reference, and associated findings.

## 7. Indexes

Create indexes based on the dashboard and investigation queries.

Recommended initial indexes:

- Unique index on normalized `Users.email`.
- Unique index on `DetectionRules.name`.
- Unique index on `SecurityPolicies.name`.
- Index on `Endpoints(application_id, is_active)`.
- Index on `SecurityEvents(created_at)`.
- Index on `SecurityEvents(application_id, created_at)`.
- Index on `SecurityEvents(decision, created_at)`.
- Index on `SecurityEvents(correlation_id)`.
- Index on `ThreatFindings(event_id)`.
- Index on `ThreatFindings(category_snapshot, severity_snapshot)`.
- Index on `AuditLogs(created_at)`.
- Index on `AuditLogs(user_id, created_at)`.

Indexes must be validated against actual query plans and data volume. Avoid adding indexes indiscriminately because they increase storage and write overhead.

## 8. Transaction and Retention Strategy

### Event Persistence

1. Complete request validation and detection.
2. Calculate the risk score and policy decision.
3. Begin a database transaction.
4. Insert the security event.
5. Insert all associated findings.
6. Commit the transaction.
7. Only then may an allowed request proceed to the controlled demo target.

If the transaction fails, roll it back and do not forward the request.

The application must handle a failure occurring after the target receives a request separately from a database write failure. The MVP should avoid retries that could accidentally duplicate non-idempotent target actions.

### Retention

The proposed retention period for security events and their associated findings is 30 days.

- Delete expired findings and events safely, preserving foreign-key integrity.
- Execute cleanup through a controlled scheduled task or maintenance process.
- Keep audit-log retention separate.
- Document the actual retention settings used in the deployed environment.
- Do not claim automatic deletion is implemented until the cleanup process has been built and tested.

## 9. Security and Azure Configuration

- Use Azure SQL Database with encrypted connections.
- Prefer managed identity for Azure-hosted application-to-database authentication when supported by the selected hosting configuration.
- If managed identity is not available, store credentials in Azure Key Vault and retrieve them securely.
- Restrict database networking to required application access paths.
- Grant the application only the database permissions it needs.
- Use a separate migration identity or deployment process for schema changes where practical.
- Never commit connection strings containing secrets to Git.
- Use parameterized SQL queries and validate data at API boundaries.
- Configure appropriate database auditing and application monitoring.
- Test backup, restore, and retention procedures appropriate to the project scope.

## 10. DP-900 Analytics Use Cases

Azure SQL Database will support relational querying and aggregation for the dashboard.

Required initial reports:

1. Total inspected events by hour, day, or week.
2. Allow and Block counts over a selected time period.
3. Findings grouped by category and severity.
4. Risk-score distribution.
5. Most-targeted registered applications and endpoints.
6. Recent high-severity or critical findings.
7. Event-processing failures, where safely captured.

Use UTC consistently for timestamps and document any display-timezone conversion performed by the frontend.

## 11. Implementation Acceptance Criteria

- All tables and foreign keys are created by version-controlled migrations.
- Unique constraints and check constraints reject invalid data.
- Endpoint/application relationships cannot be inconsistent.
- A security event and its findings are committed atomically.
- Critical findings always cause a Block decision.
- Risk scores remain within 0–100.
- Failed required persistence prevents forwarding.
- Analytics aggregates match the underlying stored data.
- Expired security events and findings are removed according to the implemented retention process.
- Database access uses secure authentication and least-privilege permissions.
- Tests verify both successful operations and expected failures.

## 12. Outstanding Implementation Decisions

The following items must be resolved before production deployment:

- Exact migration tooling and migration workflow.
- Whether policy configuration is global or selected per registered application.
- Final foreign-key deletion actions.
- Whether confidence values will be produced by every detector or remain nullable.
- Exact audit-log retention period.
- Azure SQL networking and identity settings for the selected hosting service.

These decisions must be reflected in the implemented migrations and deployment configuration. This document describes the proposed schema and is not evidence that the database has already been deployed or secured.
